What this is

A goal like "increase procurement productivity by 10%" is not one kind of work. You frame the measure. You collect what people already know. You pull an extract apart. You prototype one rule. You write the recommendation.

Today each of those lives in a different tool. The plan is in a tracker. The numbers are in a notebook. The research is in browser tabs. The recommendation is in a deck. Nothing crosses between them except a person who remembers all four.

One file now holds every one of the four. It is a markdown file. Prose stays prose, and each other part is a brick.

Words

Read this table first. Every later section uses these words and no others.

wordmeans
brickone part of the document. A fence or a comment wrap. A code cell, a question, a goal, a task, a clipping.
proseordinary markdown between bricks. It needs no markup of its own.
regionthe bricks under one heading. The headings make the regions, so nobody writes one.
basketthe exact list of bricks that one question sends to the model.
scopehow a question gathers its first set of bricks. page, region, upstream, doc or none.
pina brick a question always reads, whatever the scope says. A mute is the opposite.
budgethow many characters a question may send. The goal and the pins survive it.
upstreamthe bricks a brick reads from. Read off the code, never drawn by hand.
bundleone unit of change. It claims a region, names a goal, and owns a list of files.
snippeta brick that cites code out of a file. It holds no copy of that code.
canvasthe second view of the document. The same bricks, with coordinates.

The block is canvas and the file is *.canvas.md. An earlier draft of this work was a separate package called pata, from the Sanskrit pata, the cloth a painter paints a scroll on. That name is gone, and canvas is the only name now.

Why it helps

A notebook picks context by position: every cell above the question. That is right for a script, where the cells above are the steps you took. A plan holds four lines of work at once. Position therefore hands the recommendation question three failed attempts at a groupby. The alternative is to turn it off and paste the same paragraphs again.

An audit shows the limit. It belongs to the question near the top of the document and to the risk question near the bottom, and to nothing between them. Where a brick sits says nothing about which questions it answers.

A document that can say it gives three things.

A question shows its basket before it runs: each brick, why it is there, and what it costs. Mute one and the count drops.

A boundary on the canvas is a change you can review. It names the goal, owns the files, and holds the tasks, the prose and the code together. One page therefore answers whether the change does what the goal said.

A goal shows what serves it, and shows a goal that nothing serves. The second is the worse finding, because it looks like a goal that is going well.

The file

A pata document is one markdown file. Prose stays prose. Each other part is a brick. A brick is a fence or a comment wrap.

The reader reads the file line by line. It does not use one pattern on the whole file. This is necessary. A document about canvases shows fences as examples. A fence inside a longer fence is an example. It is not a brick.

The TICKS branch does the work. It sees a plain fence, puts the fence into the prose, and skips to the end of it. Nothing inside that fence becomes a brick. This page is such a document, and it reads correctly.

Headings are the regions of the document. Nobody writes a region. The reader gives each brick the heading above it.

The basket

Each question carries a rule. The rule says what the question may read. resolve turns the rule into the exact list that the turn will send.

The list is the point. resolve gives back items, not one string. The same list draws the panel and builds the prompt. What a person sees is what the model gets.

Four rules, in order. The goal goes in first. Then each pin. A pin that no longer exists becomes a missing item. It is visible. A silent drop is worse, because the person still believes the pin is there.

A scope gives the first set of bricks. page is the notebook rule. region is the section that you work in. upstream is what the question reads from.

The budget cuts the list. Two rules must hold. The goal and the pins stay. A pin that is larger than the whole budget gets shorter; it does not go.

The last block is the one that matters. If every item that is left is pinned, the code cuts each item to a share of the budget and marks it. It never drops a pin.

The markup is <cell> with a compact attribute. This is Leela's own notebook shape, and the choice is deliberate. Ramabana drops <cell> elements when a prompt is too large for the window. A document that wrote <block> would lose that net.

The wiring

upstream reads the code. It does not read a diagram. A name belongs to the brick that binds it. A diagram beside the code goes wrong; the code does not.

defs_of finds each name that a cell binds at the top level of its code. It looks inside if, for, try and with. It does not look inside a def, because a name in a function belongs to the function.

Three additions reach where the code cannot see.

A question anchors on the brick above it. "Fix that" means that brick and all that it reads.

A name in backticks is a name that the question reads. Write `triage` and the brick that defines triage goes in.

supports=, refutes= and blocks= state a relation between two bricks. No code states these.

The change

A region groups bricks to read. A bundle brick claims its region as one change. The boundary on the canvas is then the thing that a reviewer opens.

The files come from the code first. A code brick with #|export writes a module. Leela therefore knows the module path. paths= adds only what the bricks do not write.

A list that a person keeps by hand goes out of date. A claim that is out of date is worse than no claim, because a reviewer trusts it.

coverage holds the claim against the diff. It reports three things. Two of them are new.

matched is a file that the bundle claims and the diff changed. unmet is a file that the bundle claims and the diff did not change. unclaimed is a file that the diff changed and no bundle explains.

No diff tool can find unclaimed. Only the document knows what the change had to be.

pr cuts a pull request from one change. It gives back the title, the branch, the body, the files and the attachments. It opens nothing. Git belongs to gheasy. The forge belongs to pullup.

The _reasoning line is the part that a diff never has. Each question inside the change, with the answer that it got, goes into the body in a fold.

The value

state comes from the document. No person sets it. A status that a person must remember is a status that lies.

One case needed care. No diff is no evidence about files. It must not read as evidence against them. Without this line, a finished change reports todo.

value builds the third document. Each goal gets a region. Each change that names the goal goes under it.

Two negatives are the reason for the view. A change that serves no goal is work that the plan did not ask for. A goal that nothing serves looks like a goal that is going well, until the date arrives.

The prompts

explain drafts the prose above each snippet, and the renderer invents none of it. lit draws, and explain writes.

This package holds no writing rules. write_docs is a ramabana pyskill, and rule_text reads it from wherever ramabana installed it. Leela's rule is that no repository holds a copy of a writing skill. A prompt with the rules pasted in would be that copy.

The function raises when a skill is missing. It does not fall back to a copy, because a silent fallback would put the wrong register on the page. A caller without shalya passes the rule text through rules= instead.

Two files in the package hold the prompt itself. explain.md is the template. ste.md states the ASD-STE100 limits for this output: one idea in one sentence, 20 words at most, present tense, active voice, one word for one meaning.

prompt_for fills the template. The context comes from resolve, which is the same basket a question in the document would send. One context engine serves the reader and the drafter.

explain writes each answer into the brick and marks it wrote=ai. The document stays the record. git diff therefore shows the drafting, and a person can edit a sentence and delete the mark.

A brick that already has a body is left alone. A sentence a person wrote is the one to keep. overwrite is the only way past that rule.

ask(prompt, brick) is the host's. Nothing here imports a model. Leela passes its own assistant. capture and replay stand in when no model is reachable: capture writes the prompts out, and replay answers from a file.

This page

review builds a document from a diff. lit draws a document as one column for a phone.

A snippet brick cites code. It does not hold a copy. snip reads the file and finds the symbol in it. This page cannot show code that the file no longer has.

Each long snippet and each long diff arrives folded. A phone screen holds about 20 lines.

The diff body scrolls sideways inside its own box. The page does not scroll sideways. This is the one rule that most diff pages get wrong on a phone.

review now puts the prose next to the file that it explains. A document that explains its files therefore gives a literate diff without more work.

Five faults came out of writing the tests and this page.

A context=discard brick left the budget in document order, and not first. The item carried the scope that chose it, and not the mode of the brick.

state reported todo for a finished change whenever a caller passed no diff.

The # %% text form tore a brick in two when the prose quoted the marker. The markdown form removed that fault, because prose is prose.

A comment wrap had to fit on one line. This document's own bundle has five attributes. The reader now joins the lines until it finds -->.

Two headings with only prose between them became one region. The second heading never started a section. The reader now splits prose at each heading.

That branch also has the reactive runtime, the embedded components and the eight canvas_* agent tools. This branch has the basket, the change bundle and the three views.
